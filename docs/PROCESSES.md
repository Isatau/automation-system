# Бизнес-процессы RestoCore

## 1. Жизненный цикл заказа

```
created → open → sent → cooking → ready → awaiting_payment → paid → closed
   │        │      │       │        │            │
   └────────┴──────┴───────┴────────┴────────────┴──→ cancelled (только с причиной; из paid/closed — только возврат)
```

Правила переходов (машина состояний в `order_service.py`):
- `created/open`: редактирование состава свободно; каждое изменение — событие аудита.
- `sent` и далее: изменение/удаление позиции допустимо, но создаёт kitchen cancel-event и запись истории; начатое приготовление не «отменяется молча» — позиция получает status=cancelled с причиной, история сохраняется.
- `awaiting_payment` — при полном выставлении счёта (prebill) или после готовности всех позиций.
- `paid` — когда Σ подтверждённых платежей ≥ итога; `closed` — финальный статус (печать чека/закрытие смены).
- Конкурентное изменение: колонка `version`; PATCH с устаревшей версией → 409 Conflict, клиент перезагружает заказ.

## 2. Оплата (инварианты)

1. `Σ payments.confirmed + new ≤ order.total − Σ refunds` — проверяется в транзакции с блокировкой строки заказа.
2. Повторная оплата закрытого/оплаченного заказа отклоняется (409), а не «создаёт новый платёж».
3. Идемпотентность: `Idempotency-Key` уникален; повтор запроса возвращает исходный платёж.
4. Смешанная/частичная/раздельная оплата: несколько платежей по split-долям; статус заказа считается от суммы.
5. Возврат: уменьшает `paid_amount`, создаёт `refund` + cash/card операцию; требует права и причины; возврат больше оплаченного невозможен.
6. Чаевые хранятся отдельно (`tip`) и не входят в базу налогообложения/себестоимости.
7. Депозит/сертификат/бонусы списываются записями `deposit_operations`/`bonus_operations` в той же транзакции.
8. Фискализация отделена: платёж становится `confirmed` внутренне, `fiscal_state` = pending→done|failed двигается интеграционным слоем; при недоступности ККМ операция остаётся в очереди retry и помечается как нефискализированная (уведомление ответственному). Реальный ШК выдаётся только подтверждением адаптера.

## 3. Кассовая смена

Формула ожидаемого остатка наличных:

```
expected = initial_cash
         + Σ наличных платежей смены
         − Σ наличных возвратов
         + Σ внесений (cash-in)
         − Σ изъятий (cash-out)
         + Σ transfer_in − Σ transfer_out
diff = actual_cash − expected   (недостача < 0, излишек > 0)
```

- Открытие: касса, ответственный, начальный остаток, серверное время. Одна открытая смена на кассу.
- Закрытие: расчёт по способам оплаты, фактический пересчёт, diff, итоговый отчёт; статус closed, closed_by/at.
- Закрытая смена неизменяема: любые правки только через `/reopen` (право shifts:reopen) с причиной; повторное закрытие увеличивает reopen_count и пишет события аудита.

## 4. Продажа → склад (списание по техкарте)

При переходе заказа в `paid` для каждой позиции с `track_stock=true`:
1. Берётся действующая техкарта блюда (на дату операции).
2. Норма × количество × коэффициент пересчёта UOM → движение `-qty` типа `sale` по складу заведения (FIFO по партиям/срокам).
3. Недостаток → ошибка проведения; списание «в минус» только с правом `warehouse:negative` и причиной (движение помечается).
4. Все движения — в append-only `stock_movements`; баланс `stock_balances` — производный кэш, восстанавливается свёрткой журнала.
5. Полуфабрикаты разворачиваются рекурсией по картам.

## 5. Кухня/бар

- `/orders/{id}/send` создаёт tickets по станциям блюд (кухня/бар/grill), статус pending, sent_at=server time.
- KDS: старт (cooking, started_at), готово (done, done_at → уведомление официанту), отмена (cancel с причиной; уже cooking отменяется только с сохранением истории и событием аудита).
- Просрочка: `now − sent_at > item.cook_time_norm` — подсветка на клиенте и алерт-уведомление.
- Печать: задача принтеру через адаптер; reprint инкрементирует `reprint_no` и помечает «КОПИЯ №n».
- Изменение заказа после send → событие `order.changed_after_send` в журнале.

## 6. Инвентаризация

Создание (черновик, срезы ожидаемых остатков) → ввод фактических → проведение: по каждой строке diff≠0 создаётся движение `inventory` (+/-) с unit_cost последней закупки; изменения остатков отражаются в журнале; право warehouse:inventory.

## 7. Закупки

`purchase_order`: draft → pending_approval → approved → posted (через goods_receipt) | cancelled. При приёмке сверка ordered/received, разница фиксируется в строках; цена forming history; план закупок формируется по min_stock.

## 8. Лояльность

- Начисление бонусов: процент от итога оплаченного заказа (правило лояльности), запись bonus_operation с balance_after.
- Списание: только в плате (метод bonus) ≤ балансу и ≤ max_share правила; отмена возврата — обратная запись.
- Депозит гостя: пополнение = fin_transaction + deposit_operation(in); списание на заказ = deposit_operation(out). Баланс меняется исключительно записями операций.

## 9. Зарплата

Начисление за период: база (hourly×часы по time_entries | shift×смены) + % от персональных продаж (по waiter) + премии − авансы. Каждая запись хранит `formula_snapshot` (JSON со всеми слагаемыми и источником); исправление = новая запись с ссылкой на предыдущую (история правок). Автоматические штрафы не реализуются (правовой риск) — только ручные корректировки с причиной и правом.

## 10. Уведомления

Триггеры (item.cancel, order.cancel, refund, discount>limit, big writeoff, cash diff, unclosed shift, low stock, device error, backup failed) → движок `notify.py`: проверка порога/получателей/тихих часов, антидупликация по `dedupe_key` (окно), канал internal всегда + telegram при настройке; ссылка на объект операции.

## 11. Резервное копирование

Авто по расписанию + вручную: SQLite — копируется файл БД (WAL checkpoint), Postgres — pg_dump; считается sha256; **проверка восстановления**: копия разворачивается в временную БД и сравниваются контрольные счётчики таблиц → флаг `verify_restore_ok`. Без этого флага копия не считается надёжной. Restore останавливает запись, поднимает копию, сохраняет текущий журнал аудита отдельным файлом.

## 12. Идемпотентность и конкурентность

- Ключ идемпотентности хранится с хешем запроса; другой тело-запрос под тем же ключом → 422.
- Строки заказов/смен/балансов блокируются (`FOR UPDATE` на Postgres; сериализация записи на SQLite) внутри транзакции.
- Все даты аудита — серверное время (Asia/Almaty), клиентское время не используется.
